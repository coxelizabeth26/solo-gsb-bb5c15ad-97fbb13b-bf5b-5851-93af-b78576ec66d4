# 陶瓷窑车层架载荷追踪台

按 **自下而上** 的方式录入窑车台面、各层矩形棚板（位置/尺寸/自重）、坯件重量，
以及承托该层棚板的立柱坐标与容量。系统根据立柱底端坐标自动判定它落在哪一块
下层棚板（底层落在窑车台面）上，**自上而下逐层分摊、逐层累加**立柱载荷，并在
俯视图 / 侧视图中标出三类风险立柱：

| 标记 | 判定规则 | 含义 |
| --- | --- | --- |
| 🟪 悬空 `hang` | 立柱底端坐标不在承托面（下层棚板或窑车台面）矩形内 | 该柱不受力，本层载荷改由其余有效柱承担 |
| 🟧 落点重叠 `overlap` | 同层两根及以上立柱底端平面距离 ≤ 10 mm | 踩在同一落点，对下层棚板的点载荷合并累加 |
| 🟥 超载 `overload` | 立柱实际分配载荷 > 该柱容量 | 立柱过载，需要加柱 / 减载 / 换大容量柱 |

点击任意立柱可查看其 **载荷来源明细**（本层棚板自重、坯件、以及从更上层逐级
传递下来的每一根立柱的贡献链，例如 `第三层（顶层）·P5 → 第二层·P1`）；
点击棚板可查看该板的承受/下传载荷汇总。**修改任一层输入后整架自动重算**
（250 ms 防抖）并保存到服务端，刷新页面不丢数据。

另有 **立柱失效推演（What-if）**：在结果区勾选一根或多根非悬空立柱为“失效柱”，
系统以当前编辑数据为基准，把失效柱视为不承载后按原规则整架重新分摊，
并排对比基准/推演的台面载荷、丢失载荷与每根立柱载荷差值，并单独列出推演
新增的超载/无支撑项；失效标记只存在于会话内、**不保存**，清空选择立即恢复基准。

还有 **加柱建议**：选择目标层、设置候选网格间距与新柱容量后，后端仅在该层
**承托面内**、且与现有**有效柱**底端距离严格大于重叠阈值（10 mm）的网格点上，
逐点试算新增一根立柱，按「丢失载荷 → 超载数 → 最高利用率（容量 0 不计）→
坐标」升序返回前 5 个方案。面板并排对比基准与各方案的**逐层载荷**与
**新增/消除告警**；点击方案即在俯视图预览新柱位置，**确认后才写入架体并
触发原有自动保存**，取消预览不改动任何数据；没有可行点时会明确给出限制原因。

另有 **减载配额试算（Relief Quota）**：以当前架体为基准，**只调整各层坯件
重量**（棚板、立柱、坐标均不变），在每层减量不超过现有坯件重量的条件下，
求让所有**有限容量立柱**（容量 0=不限，不参与）不再超载的**最小总减载量**；
多层载荷按现有整架分摊规则共同传到下层，求得方案后会再做一次**整架校验**。
面板逐层列出**原坯件重量 → 建议重量 → 减量**，以及减载前后各层本层总载荷、
超载柱数、丢失载荷、下传载荷与整架汇总。试算**不写入状态**，俯视图/侧视图
仅预览减载后的重校结果，**确认后才更新坯件重量并沿用自动保存**，继续编辑
架体会立即使旧方案作废；若全部坯件清空仍有超载柱，会明确提示**无解**并
列出剩余超载柱（载荷/容量），此时建议考虑加柱或更换大容量柱。

## 一条命令启动

需要本机已安装 Docker（含 Compose 插件 v2）。

```bash
docker compose up --build -d
```

启动后浏览器访问：

> **http://localhost:8000**

首次启动会自动把内置 **示例数据**（`data/sample_state.json`，一个 3 层窑车，
内含悬空、落点重叠、超载各一例）复制为可编辑的 `data/state.json`；之后所有
编辑都保存在这个文件里，容器重启数据不丢（通过 `./data` 目录挂载）。
减载配额试算、失效推演、加柱建议均为纯计算接口，**不写盘**，无需额外配置。

停止 / 查看日志：

```bash
docker compose down        # 停止
docker compose logs -f     # 查看日志
```

## 必要配置

默认无需任何配置。仅当 8000 端口被占用时，在启动前指定宿主机端口：

```bash
HOST_PORT=9000 docker compose up --build -d   # 访问 http://localhost:9000
```

也可以创建 `.env` 文件持久化该配置：

```env
HOST_PORT=9000
```

| 配置项 | 位置 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `HOST_PORT` | compose 环境变量 | `8000` | 宿主机映射端口 |
| `PORT` | 容器环境变量 | `8000` | 容器内 gunicorn 监听端口（一般无需改） |
| `KILN_DATA_DIR` | 容器环境变量 | `/app/data` | 状态 JSON 存放目录，已挂载到宿主机 `./data` |

恢复内置示例：页面右上角 **「↺ 恢复示例」** 按钮（会覆盖当前编辑），
或删除宿主机 `data/state.json` 后重启容器。

## 操作说明

1. **录入架体**：左侧面板自下而上编辑台面尺寸、各层棚板（位置/尺寸/自重）、
   坯件重量与立柱（底端坐标/容量）；任意修改约 250 ms 后整架自动重算并保存，
   顶栏显示保存状态，刷新页面不丢数据。
2. **查看结果**：右侧俯视图 / 侧视图实时刷新；点击立柱或棚板查看载荷来源链；
   「告警与判定」列出悬空、落点重叠、超载、无支撑等问题，点击条目可定位到
   对应立柱/棚板。
3. **立柱失效推演**：在结果区「🔮 立柱失效推演」面板勾选一根或多根
   **非悬空**立柱（悬空柱本就不承载，不可勾选）：
   - 系统以当前编辑数据为基准，将失效柱视为不承载后整架重新分摊；
   - 面板并排显示基准 → 推演的**台面载荷**、**丢失载荷**及**每根立柱载荷差值**，
     并单独列出推演后**新增的超载 / 无支撑项**（点击条目可定位）；
   - 视图中失效柱为粉色 ⊘ 标记（原悬空柱仍为紫色 ✕），点击任意立柱仍可查看
     推演后的载荷来源链；失效柱明细会标注其基准载荷去向；
   - 失效标记仅本次会话有效，**不会改写或自动保存**架体数据；
     点击「✕ 清空选择 · 恢复基准」立即回到基准结果；
   - 推演进行中继续编辑架体，会以新数据为基准自动重跑推演。
4. **加柱建议**：在结果区「🧱 加柱建议」面板选择**目标层**，填写候选网格间距
   （mm）与新柱容量（kg，0=不限容量），点击「开始试算」：
   - 后端在该层承托面（底层为窑车台面，其余为下层棚板）内按网格逐点试算，
     仅保留落在承托面内、且与现有**有效柱**距离严格大于 10 mm（`TOL_MM`）
     的候选点；每个点都按原规则整架重算一次；
   - 结果按 **丢失载荷 → 超载柱数 → 最高利用率（容量为 0 的柱不计利用率）
     → 坐标 (x, y)** 全部升序，只返回前 **5** 个方案；
   - 每个方案卡片展开后列出基准 → 方案的**逐层**本层总载荷、丢失载荷、
     下传载荷、超载柱数，以及**新增告警 / 消除告警**（点击条目可定位）；
   - 点击方案卡片，俯视图用金色 ⊕ 标记**预览**新柱落点与试算后载荷；
     此时架体数据**不会改变**，点「✕ 取消预览（不改数据）」随时撤销预览；
   - 点「✓ 确认加柱并保存」才会把该柱追加到目标层，随后走原有编辑通道
     自动重算并保存；继续编辑架体会使旧的试算结果自动作废，需要重新试算；
   - 若承托面为空、候选点全部落在重叠阈值内、或网格过密（> 4096 个候选点），
     面板会明确说明限制原因与调整建议（加大间距 / 调整现有柱 / 更换目标层）。
5. **减载配额试算**：在结果区「⚖️ 减载配额试算」面板点击「开始试算」：
   - 后端以当前架体为基准，**只调各层坯件重量**（每层 0 ≤ 减量 ≤ 现有坯件
     重量），按「刚性棚板、有效柱均摊、多层载荷向下累计」的同一套分摊规则，
     求消除全部有限容量柱超载的**最小总减载量**（不支撑层链断开，其坯件
     减量不参与）；建议重量按 0.01 kg 向下取整后再**重新整架校验**，
     有取整残差会自动补齐；
   - 面板给出整架「超载柱数、最小总减载量、传到台面、丢失载荷、总自重」
     减载前后对比，并逐层列出原坯重、建议重量、减量及本层总载荷 / 丢失 /
     下传 / 超载柱数的前后变化（点击剩余告警可定位到立柱/棚板）；
   - 试算期间俯视图 / 侧视图 / 明细均切换为减载后的重校结果（汇总区出现
     「⚖️ 减载预览中」标记）；点「✕ 取消预览（不改数据）」恢复基准，
     试算结果仍保留；
   - 点「✓ 确认按建议重量更新并保存」会弹出逐层变更清单，确认后仅更新
     坯件重量并走原有编辑通道**自动重算并保存**；此后任意架体编辑
     （或恢复示例）都会自动清除旧方案，需要重新试算；
   - **无解**：即使全部坯件清空仍有超载柱时，面板明确提示无解，列出清空
     后的剩余超载柱（层 / 编号 / 载荷 / 容量），此时应加柱、换大容量柱
     或减轻棚板自重——减坯件已无法解决。

## HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/state` | 读取当前架体输入（首次自动生成示例） |
| `PUT` | `/api/state` | 保存架体 JSON，并返回整架重算结果（前端每次编辑调用） |
| `POST` | `/api/recalc` | 仅重算：body 传架体 JSON（不传则用已保存状态） |
| `GET` | `/api/result` | 已保存状态的重算结果 |
| `POST` | `/api/simulate` | 立柱失效推演：body `{"state": 架体JSON(可省), "failed": [{"layer": 0, "post": "P1"}]}`，返回 `{baseline, simulation, failed, diff}`（基准/推演/生效失效柱/差值）；**只计算，不写盘**，失效标记不持久化 |
| `POST` | `/api/suggest` | 加柱建议：body `{"state": 架体JSON(可省), "layer": 2, "spacing": 100, "capacity": 300}`；在目标层承托面内按候选网格逐点试算新增一根立柱，按丢失载荷/超载数/最高利用率/坐标升序返回前 5 个方案（含逐层载荷与新增/消除告警对比）；**只计算，不写盘**，参数非法返回 400，无可行点返回 200 + `reason`；确认加柱由前端走 `PUT /api/state` 完成 |
| `POST` | `/api/relieve` | 减载配额试算：body `{"state": 架体JSON(可省)}`；只调各层坯件重量求消除全部有限容量柱超载的最小总减载量，返回 `feasible`、逐层 `wareWeight/suggestedWeight/reduction`、减载前后超载数/丢失载荷/台面载荷对比与整架重校 `result`；**只计算，不写盘**；无解时 `feasible=false` 并给出全部坯件清空后的 `remainingOverloads`；确认更新由前端走 `PUT /api/state` 完成 |
| `POST` | `/api/reset` | 恢复内置示例数据 |

## 载荷模型与约定

- 坐标系：俯视平面为 XY，原点在窑车台面左下角，X 向右、Y 向上，单位 mm；Z 为高度方向。
- 每层包含一块矩形棚板 `(x, y, w, d)` 与若干立柱；立柱**顶端托住本层棚板、
  底端落在下一层棚板上**，底层立柱底端落在窑车台面矩形内。
- 第 i 层棚板承受总载荷：
  `棚板自重 + 坯件重量 + 所有落在本板上的上层立柱点载荷`。
- 采用 **刚性棚板、有效立柱均摊** 的工程简化：总载荷由本层所有非悬空立柱
  平均分配；悬空立柱载荷为 0。若整层无有效立柱，该层载荷记为“丢失载荷”，
  不再向下传递，汇总区单独显示。
- 同层立柱底端距离 ≤ **10 mm**（`app/calc.py` 中 `TOL_MM`，可调）判定为落点
  重叠，合并为一个点载荷施加到下层棚板。
- 容量留空或填 0 表示“不限容量”，不参与超载判定。
- 顶层以上没有棚板：顶层立柱只承担把顶板载荷向下传递的作用。
- 失效推演：`POST /api/simulate`（或 `calc.calculate(state, failed=[...])`）把指定
  **非悬空**立柱标记为失效（输出 `failed=true`），视为不承载后整架按同一规则
  重新分摊；失效柱与悬空柱分开计数（`failedCount`），不触发悬空告警，只产生
  info 级提示，且不参与落点重叠判定与点载荷下传。
- 加柱建议：`POST /api/suggest`（或 `calc.suggest_posts(state, layer, spacing,
  capacity)`）在目标层承托面矩形内按 `spacing` 生成候选网格（自承托面左下角
  起，含边界），剔除与现有**非悬空**柱距离 ≤ `TOL_MM` 的点（严格大于才可行），
  对每个可行点深拷贝架体、追加一根新柱后调用同一套 `calculate` 整架重算，
  按 `(lostLoad, overloadCount, maxUtilization, x, y)` 升序取前 5；利用率只统计
  `capacity > 0` 的柱（容量 0 视为不限容量、不参与，全部不计时该方案利用率
  排最后）。候选点超过 4096 个（`MAX_SUGGEST_GRID`）直接返回加大间距的提示，
  不做穷举。整个过程不修改输入、不写盘；用户在前端确认后才通过
  `PUT /api/state` 持久化。
- 减载配额试算：`POST /api/relieve`（或 `calc.relieve_load(state)`）利用
  均摊模型的线性性质：同层每根有效柱载荷恒为 `T_i / c_i`（与上层点载荷
  落点/重叠无关，落点只影响下传点的合并，不改变下传总量），故
  `T_i(d) = T0_i − Σ_{同链高层} d_j` 为坯件减量 `d_j` 的后缀线性和；
  第 i 层有限容量柱不超载等价于 `T_i ≤ c_i · min(capacity>0)`。遇不支撑
  层（无有效柱）链断开、该层载荷整层丢失，减其坯件无益于任何约束。
  求解把各约束所需后缀减量**自上而下优先放到链内最高层**（高层减量覆盖
  自身及下方全部约束），一遍贪心即得最小总减量；全部坯件清空（
  `d_i = 现有坯件重量`）仍满足不了某约束即无解。建议重量按 0.01 kg
  向下取整后用同一套 `calculate` **重新整架校验**，取整残差每次自超载
  最高层起再减 0.01 kg 直至零超载。整个过程不修改输入、不写盘；用户在
  前端确认后才通过 `PUT /api/state` 持久化。
